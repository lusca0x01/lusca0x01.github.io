Como "Hookar" Funções: Guia Completo de Function Hooking

20 de maio de 2026 12 minutos de leitura Engenharia Reversa

Este guia explora como interceptar e redirecionar funções em tempo de execução utilizando técnicas de Function Hooking, com foco especial em Detour Hooking (Inline Hooking). Além disso, abordaremos conceitos fundamentais como Pattern Scanning, Trampolines, Relay Functions e estratégias utilizadas para localizar e manipular funções mesmo em binários sem símbolos.

O que é Function Hooking?

Function Hooking é uma técnica utilizada para interceptar, monitorar ou redirecionar chamadas de funções em tempo de execução, permitindo alterar o comportamento original de uma aplicação sem modificar diretamente seu código-fonte ou recompilá-la.

O código responsável por interceptar e manipular essas chamadas é chamado de hook.

Na prática, o objetivo do hooking é fazer com que, ao invés da execução seguir para a função original, ela passe primeiro por um código personalizado, que pode:

  • Alterar parâmetros
  • Modificar valores de retorno
  • Registrar informações (logging)
  • Bloquear execuções
  • Redirecionar completamente o fluxo do programa

Essa técnica é amplamente utilizada em:

  • Debuggers (como WinDbg, x64dbg)
  • EDRs e antivírus
  • Engenharia reversa
  • Instrumentação de software
  • Overlays e mods de jogos
  • Monitoramento de APIs
  • Sistemas de profiling
  • Mecanismos de compatibilidade

Quais os tipos de Function Hooking?

Existem diversas técnicas diferentes de hooking. Dentre elas, podemos citar:

Import Address Table Hooking (IAT Hooking)

Substitui o ponteiro original de uma função na Import Address Table (IAT) por outro. É uma abordagem menos invasiva e frequentemente usada para hooks de nível de aplicação.

Export Address Table Hooking (EAT Hooking)

Segue o mesmo princípio, mas utiliza a tabela de exportação (EAT) da DLL ao invés da tabela de importação. Útil para hookar funções exportadas por uma DLL.

VTable Hooking

Utiliza o conceito de Virtual Tables (VTables) do C++ para alterar os ponteiros de métodos virtuais. Particularmente útil em aplicações orientadas a objetos.

Foco do Artigo

Entretanto, neste artigo iremos focar no Detour Hooking (também conhecido como Inline Hooking), uma técnica que altera diretamente o fluxo de execução da função original, geralmente sobrescrevendo suas primeiras instruções com um salto (JMP) para uma função personalizada.

Detour Hooking (Inline Hooking)

Imagine a função MessageBoxA da API do Windows. Quando uma aplicação chama essa função, o fluxo de execução normalmente segue diretamente para a implementação original presente na user32.dll.

Os bytes pertencentes à DLL normalmente ficam em páginas marcadas como leitura e execução (RX — Read/Execute), impedindo modificações. Entretanto, APIs do sistema operacional como VirtualProtect permitem alterar temporariamente as permissões para escrita (RWX ou RW).

Como funciona:

Em um Detour Hook, alteramos os primeiros bytes (geralmente os primeiros 5 bytes, que nos permitem realizar um 32-bit relative jump) dessa função na memória para que, ao invés da execução continuar normalmente, ela seja desviada para uma função controlada por nós.

Imagine que o início original da função seja (algo comum na criação de stack frames):

MessageBoxA:
push rbp
mov rbp, rsp
sub rsp, 30h

Em bytes, isso seria algo semelhante a:

55                ; push rbp
48 89 E5          ; mov rbp, rsp
48 83 EC 30       ; sub rsp, 30h

Substituímos os primeiros bytes por um JMP relativo:

jmp HookedMessageBoxA; localizada em 0x12345678

O opcode é E9 <offset>, onde o offset é calculado como:

Destino - (Instruction Pointer Atual + 5)

Os 5 bytes representam:

1 byte do opcode E9
4 bytes do offset

Na prática o início da função passa a ser:

E9 12 34 56 78    ; jmp HookedMessageBoxA
83 EC 30          ; Bytes que não foram sobrescritos

O Problema: Instruções Corrompidas

Ao sobrescrever os primeiros bytes da função original com o JMP, destruímos instruções legítimas. Isso significa que, caso tentemos executar a implementação original posteriormente, parte do código necessário já terá sido perdida.

Exemplificando:

; Originalmente:
55                ; push rbp
48 89 E5          ; mov rbp, rsp
48 83 EC 30       ; sub rsp, 30h

; Após o hook:
E9 12 34 56 78    ; jmp HookedMessageBoxA
83 EC 30          ; Bytes que não foram sobrescritos

; Bytes originais perdidos:
55
48 89 E5
48

Ou seja, a função original ficou parcialmente corrompida. Além disso, não podemos sobrescrever "metade" de uma instrução. Como instruções x86/x64 possuem tamanho variável, é necessário sobrescrever instruções completas até atingir o tamanho mínimo necessário para o hook.

A solução: Trampoline + Relay Function

Trampoline

O Trampoline é responsável por preservar e executar os bytes originais sobrescritos pelo hook.

Ele funciona da seguinte forma:

  • copia as instruções originais removidas da função;
  • executa essas instruções em outra região de memória;
  • realiza um salto de volta para a continuação da função original.

Exemplo conceitual:

; Bytes copiados da função original
push rbp
mov rbp, rsp

; Retorna para MessageBoxA+5
jmp MessageBoxA+5

Dessa forma, conseguimos continuar a execução legítima da função mesmo após alterar seus primeiros bytes.

Relay Function

Já a Relay Function atua como uma função intermediária entre o hook e a função original.

Ela normalmente possui dois objetivos:

  • encapsular lógica auxiliar;
  • facilitar o redirecionamento do fluxo.

Em arquiteturas x64 isso é especialmente importante, porque o jmp rel32 possui alcance limitado a ±2GB.

Caso nossa função de hook esteja muito distante da função original na memória, não conseguimos alcançá-la diretamente utilizando apenas o opcode E9.

Nesse cenário, criamos uma pequena função intermediária próxima da função original: 

RelayFunction:
mov rax, HookedMessageBoxA
jmp rax

A Relay Function então realiza o salto absoluto para o hook real.

Então o fluxo fica:

MessageBoxA (hooked function)
    → Relay Function
        → Hook (HookedMessageBoxA)
            → Trampoline
                → MessageBoxA (continuação)

Mas e se não soubermos quem é a Função?

É muito comum que, ao analisarmos uma aplicação, não exista PDB ou qualquer tipo de referência para nomes e assinaturas de funções.

Em muitos casos, temos apenas um binário compilado e completamente "cego" (stripped), sem símbolos, nomes ou documentação.

Ainda assim, ferramentas como x64dbg, IDA, Ghidra ou Cheat Engine permitem analisar o comportamento do programa em tempo de execução.

Um exemplo clássico, voltado ao mundo dos jogos, é encontrar uma variável de vida (health) que aumenta ou diminui após uma determinada ação dentro do jogo.

Encontrando a Função pelo Comportamento

Imagine que a vida do jogador vale:

100

Após receber dano:

75

No Cheat Engine, podemos procurar:

First Scan → 100
Next Scan → 75

Até encontrarmos o endereço responsável pela variável.

"Who writes to this address?"

Depois disso, podemos utilizar uma funcionalidade extremamente importante: 

Find out what writes to this address
ou
What accesses this address

Então, ao tomar dano novamente, o debugger intercepta a instrução responsável: 

sub [rcx+14], eax
ou
mov [rbx+10], eax

Nesse momento, mesmo sem saber o nome da função, descobrimos:

  • qual instrução altera a vida;
  • qual registrador contém a estrutura do jogador;
  • onde o código responsável está na memória.

Subindo para a Função

Agora podemos abrir o disassembler e analisar o código ao redor daquela instrução: 

Game.exe+123456:
48 89 5C 24 08
57
48 83 EC 20
29 41 14          ; sub [rcx+14], eax

Mesmo sem símbolos, conseguimos identificar:

  • prólogo da função;
  • fluxo de execução;
  • chamadas;
  • condicionais;
  • registradores utilizados.

Ou seja: encontramos a função através do comportamento dela.

Pattern Scanning

Pattern Scanning (também conhecido como Signature Scan ou AOB Scan) é uma técnica utilizada para localizar regiões específicas de código na memória através de sequências de bytes características de uma função ou trecho de instrução.

Essa abordagem é extremamente útil quando:

  • não possuímos símbolos (PDB);
  • os endereços mudam entre execuções;
  • ASLR está habilitado;
  • a aplicação recebe atualizações constantes;
  • não sabemos o nome da função;
  • não temos acesso ao código-fonte.

Em vez de procurar nomes ou endereços fixos, procuramos padrões de instruções que identificam aquele trecho de código.

Como funciona?

Imagine que identificamos a seguinte sequência durante a análise: 

48 89 5C 24 08
57
48 83 EC 20
29 41 14

Podemos transformá-la em uma assinatura:

48 89 5C 24 08 57 48 83 EC 20 29 41 14

O scanner então percorre a memória do módulo byte por byte tentando encontrar exatamente aquela sequência.

Wildcards

Nem todos os bytes são estáveis entre execuções ou versões.

Instruções como:

call Game.exe+123456
jmp Game.exe+ABCDEF
mov rax, 7FF712341000h

podem conter:

  • offsets relativos;
  • endereços relocados;
  • ponteiros variáveis;
  • valores alterados pelo compilador.

Por isso, utilizamos wildcards (?) para ignorar bytes variáveis.

Exemplo:

48 89 5C 24 08 57 48 83 EC ? ? 29 41 14

Nesse caso, os dois bytes após EC podem assumir qualquer valor.

Na prática

Suponha que a memória contenha:

7FF600001000  48 89 5C 24 08
7FF600001005  57
7FF600001006  48 83 EC 20
7FF60000100A  29 41 14

O Pattern Scanner encontra:

48 89 5C 24 08 57 48 83 EC 20 29 41 14

e retorna:

7FF600001000

Criando Assinaturas Boas

Uma assinatura ruim como:

55 8B EC

pode aparecer centenas ou milhares de vezes dentro do executável.

Já assinaturas melhores:

  • são maiores;
  • possuem bytes mais únicos;
  • evitam regiões altamente variáveis;
  • sobrevivem a updates do binário.

Exemplo mais robusto:

48 89 5C 24 08 57 48 83 EC ? ? 48 8B F9

Relacionando Pattern Scanning com Function Hooking

Na prática, Pattern Scanning é frequentemente utilizado antes da instalação do hook.

Fluxo comum:

Pattern Scan
    → Encontrar endereço em runtime
        → Instalar Hook

Isso permite que o hook continue funcionando mesmo após mudanças de endereço causadas por ASLR ou atualizações da aplicação.

Conclusão

Function Hooking é uma técnica extremamente poderosa e versátil, sendo amplamente utilizada em engenharia reversa, instrumentação, debugging, análise de malware e desenvolvimento de ferramentas.

Dominar conceitos como Detour Hooking, Trampolines, Relay Functions e Pattern Scanning permite interceptar e analisar aplicações mesmo sem símbolos ou acesso ao código-fonte.

Pontos-chave:

  • Function Hooking intercepta e redireciona chamadas de funções em tempo de execução;
  • Trampolines preservam os bytes originais sobrescritos pelo hook;
  • Relay Functions ajudam a contornar limitações de alcance em x64;
  • É possível encontrar funções analisando o comportamento da aplicação;
  • Pattern Scanning permite localizar funções mesmo sem símbolos;
  • Wildcards tornam assinaturas mais resilientes a updates do binário.
