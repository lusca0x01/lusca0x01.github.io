How to Hook Functions: Complete Function Hooking Guide

May 20, 2026 18 minutes read Reverse Engineering

This guide explores how to intercept and redirect functions at runtime using Function Hooking techniques, with special focus on Detour Hooking (Inline Hooking). Additionally, we'll cover fundamental concepts such as Pattern Scanning, Trampolines, Relay Functions, and strategies used to locate and manipulate functions even in binaries without symbols.

What is Function Hooking?

Function Hooking is a technique used to intercept, monitor, or redirect function calls at runtime, allowing you to alter the original behavior of an application without directly modifying its source code or recompiling it.

The code responsible for intercepting and manipulating these calls is called a hook.

In practice, the goal of hooking is to make execution pass through custom code before reaching the original function, which can:

  • Alter parameters
  • Modify return values
  • Record information (logging)
  • Block executions
  • Completely redirect program flow

This technique is widely used in:

  • Debuggers (such as WinDbg, x64dbg)
  • EDRs and antivirus software
  • Reverse engineering
  • Software instrumentation
  • Game overlays and mods
  • API monitoring
  • Profiling systems
  • Compatibility mechanisms

What are the types of Function Hooking?

There are several different hooking techniques. Among them, we can mention:

Import Address Table Hooking (IAT Hooking)

Replaces the original function pointer in the Import Address Table (IAT) with another. It's a less invasive approach commonly used for application-level hooks.

Export Address Table Hooking (EAT Hooking)

Follows the same principle, but uses the DLL's export table (EAT) instead of the import table. Useful for hooking functions exported by a DLL.

VTable Hooking

Uses the concept of Virtual Tables (VTables) from C++ to alter pointers to virtual methods. Particularly useful in object-oriented applications.

Article Focus

However, in this article we will focus on Detour Hooking (also known as Inline Hooking), a technique that directly alters the execution flow of the original function, usually by overwriting its first instructions with a jump (JMP) to a custom function.

Detour Hooking (Inline Hooking)

Imagine the MessageBoxA function from the Windows API. When an application calls this function, execution normally flows directly to the original implementation in user32.dll.

The bytes belonging to the DLL normally reside in pages marked as read and execute (RX), preventing modifications. However, operating system APIs like VirtualProtect allow temporarily changing permissions to write (RWX or RW).

How it works:

In a Detour Hook, we modify the first bytes (usually the first 5 bytes, which allow us to perform a 32-bit relative jump) of that function in memory so that instead of continuing normally, execution is diverted to a function we control.

Imagine that the original beginning of the function is (common in stack frame creation):

MessageBoxA:
push rbp
mov rbp, rsp
sub rsp, 30h

In bytes, this would be something like:

55                ; push rbp
48 89 E5          ; mov rbp, rsp
48 83 EC 30       ; sub rsp, 30h

We replace the first bytes with a relative JMP:

jmp HookedMessageBoxA; located at 0x12345678

The opcode is E9 <offset>, where the offset is calculated as:

Destination - (Current Instruction Pointer + 5)

The 5 bytes represent:

1 byte of opcode E9
4 bytes of offset

In practice, the beginning of the function becomes:

E9 12 34 56 78    ; jmp HookedMessageBoxA
83 EC 30          ; Bytes that were not overwritten

The Problem: Corrupted Instructions

When we overwrite the first bytes of the original function with the JMP, we destroy legitimate instructions. This means that if we try to execute the original implementation later, part of the necessary code has already been lost.

Exemplifying:

; Originally:
55                ; push rbp
48 89 E5          ; mov rbp, rsp
48 83 EC 30       ; sub rsp, 30h

; After the hook:
E9 12 34 56 78    ; jmp HookedMessageBoxA
83 EC 30          ; Bytes that were not overwritten

; Original bytes lost:
55
48 89 E5
48

That is, the original function was partially corrupted. Furthermore, we can't overwrite "half" of an instruction. Since x86/x64 instructions have variable sizes, we need to overwrite complete instructions until we reach the minimum size needed for the hook.

The Solution: Trampoline + Relay Function

Trampoline

The Trampoline is responsible for preserving and executing the original bytes overwritten by the hook.

It works as follows:

  • copies the original instructions removed from the function;
  • executes those instructions in another memory region;
  • jumps back to the continuation of the original function.

Conceptual example:

; Bytes copied from the original function
push rbp
mov rbp, rsp

; Returns to MessageBoxA+5
jmp MessageBoxA+5

This way, we can continue legitimate function execution even after modifying its first bytes.

Relay Function

The Relay Function acts as an intermediary function between the hook and the original function.

It typically has two objectives:

  • encapsulate auxiliary logic;
  • facilitate flow redirection.

In x64 architectures this is especially important because jmp rel32 has limited range of ±2GB.

If our hook function is very far from the original function in memory, we can't reach it directly using only the E9 opcode.

In this scenario, we create a small intermediary function near the original function: 

RelayFunction:
mov rax, HookedMessageBoxA
jmp rax

The Relay Function then performs the absolute jump to the real hook.

So the flow becomes:

MessageBoxA (hooked function)
    → Relay Function
        → Hook (HookedMessageBoxA)
            → Trampoline
                → MessageBoxA (continuation)

But what if we don't know who the Function is?

It's very common that when analyzing an application, there's no PDB or any kind of reference to function names and signatures.

In many cases, we only have a compiled binary that is completely "blind" (stripped), without symbols, names, or documentation.

Still, tools like x64dbg, IDA, Ghidra, or Cheat Engine allow you to analyze program behavior at runtime.

A classic example, focused on the gaming world, is finding a health variable that increases or decreases after a certain action within the game.

Finding the Function by Behavior

Imagine the player's health is:

100

After taking damage:

75

In Cheat Engine, we can search for:

First Scan → 100
Next Scan → 75

Until we find the address responsible for the variable.

"Who writes to this address?"

After that, we can use an extremely important feature: 

Find out what writes to this address
or
What accesses this address

Then, when taking damage again, the debugger intercepts the responsible instruction: 

sub [rcx+14], eax
or
mov [rbx+10], eax

At this point, even without knowing the function name, we discover:

  • which instruction alters the health;
  • which register contains the player structure;
  • where the responsible code is in memory.

Going Up to the Function

Now we can open the disassembler and analyze the code around that instruction: 

Game.exe+123456:
48 89 5C 24 08
57
48 83 EC 20
29 41 14          ; sub [rcx+14], eax

Even without symbols, we can identify:

  • function prologue;
  • execution flow;
  • calls;
  • conditionals;
  • registers used.

That is: we found the function through its behavior.

Pattern Scanning

Pattern Scanning (also known as Signature Scan or AOB Scan) is a technique used to locate specific regions of code in memory through byte sequences characteristic of a function or instruction snippet.

This approach is extremely useful when:

  • we don't have symbols (PDB);
  • addresses change between executions;
  • ASLR is enabled;
  • the application receives constant updates;
  • we don't know the function name;
  • we don't have access to source code.

Instead of searching for fixed names or addresses, we search for patterns of instructions that identify that code snippet.

How it works?

Imagine we identify the following sequence during analysis: 

48 89 5C 24 08
57
48 83 EC 20
29 41 14

We can transform it into a signature:

48 89 5C 24 08 57 48 83 EC 20 29 41 14

The scanner then traverses the module memory byte by byte trying to find exactly that sequence.

Wildcards

Not all bytes are stable between executions or versions.

Instructions like:

call Game.exe+123456
jmp Game.exe+ABCDEF
mov rax, 7FF712341000h

may contain:

  • relative offsets;
  • relocated addresses;
  • variable pointers;
  • values changed by the compiler.

That's why we use wildcards (?) to ignore variable bytes.

Example:

48 89 5C 24 08 57 48 83 EC ? ? 29 41 14

In this case, the two bytes after EC can take any value.

In practice

Suppose memory contains:

7FF600001000  48 89 5C 24 08
7FF600001005  57
7FF600001006  48 83 EC 20
7FF60000100A  29 41 14

The Pattern Scanner finds:

48 89 5C 24 08 57 48 83 EC 20 29 41 14

and returns:

7FF600001000

Creating Good Signatures

A bad signature like:

55 8B EC

can appear hundreds or thousands of times within the executable.

Better signatures:

  • are larger;
  • have more unique bytes;
  • avoid highly variable regions;
  • survive binary updates.

More robust example:

48 89 5C 24 08 57 48 83 EC ? ? 48 8B F9

Relating Pattern Scanning to Function Hooking

In practice, Pattern Scanning is often used before hook installation.

Common flow:

Pattern Scan
    → Find address at runtime
        → Install Hook

This allows the hook to continue working even after address changes caused by ASLR or application updates.

Conclusion

Function Hooking is an extremely powerful and versatile technique, widely used in reverse engineering, instrumentation, debugging, malware analysis, and tool development.

Mastering concepts like Detour Hooking, Trampolines, Relay Functions, and Pattern Scanning allows you to intercept and analyze applications even without symbols or access to source code.

Key points:

  • Function Hooking intercepts and redirects function calls at runtime;
  • Trampolines preserve the original bytes overwritten by the hook;
  • Relay Functions help overcome range limitations in x64;
  • It's possible to find functions by analyzing application behavior;
  • Pattern Scanning allows you to locate functions even without symbols;
  • Wildcards make signatures more resilient to binary updates.
